## THE P1 MECHANISM (A0-9) — how a joiner gets silently, permanently stuck

`clientHandlers.ts` routes every inbound message through `route(msg, peerId)`. Before anything else:

```ts
if (deps.session.hostVerifiedPeerId === null &&
    (msg.kind === 'START_GAME_SIGNAL' || msg.kind === 'LOBBY_PRESENCE')) {
  … buffer latest-per-kind …
  return;                                   // ⛔ not applied
}
if (!hostAuthFilter(deps.session, msg, peerId)) return;   // ⛔ drops NETSNAPSHOT too
```

`hostVerifiedPeerId` is latched ONLY by `kickVerify → verifyHostAttest(attest, roomCode, senderPeerId)`,
which requires `roomCodeFromPubkey(spki) === roomCode` **and** a valid ECDSA signature over
`(roomCode ‖ senderPeerId)`. If that verification never succeeds, then for the joiner:

1. `LOBBY_PRESENCE` is buffered and never applied ⇒ `presenceRoster` stays `null`;
2. `START_GAME_SIGNAL` is buffered and never applied ⇒ **the joiner never leaves LOBBY**;
3. `NETSNAPSHOT` is dropped by `hostAuthFilter` ⇒ **the snapshot fallback that exists precisely to
   rescue a lost Begin (S39 P1) cannot fire either**;
4. and the failure is **console-only, by explicit design**: *"a spoofer's failed attest must not
   scare the user with a lobby error while the genuine host verifies fine."*

Now the owner's sentence, mapped onto that state, clause by clause:

- *"you see that player already in when trying to connect"* — with `presenceRoster === null`, the
  lobby rack falls back to **count-based** seat derivation (`lobbyStateMachine.ts:88-96`: the roster
  *"SUPERSEDES the count-based seat derivation"* when non-null). `peerCount` is transport-level and
  unaffected by verification, so the joiner sees a populated lobby **from the fallback path**.
- *"it keeps saying connected..."* — `LOBBY_STATUS.JOINED_WAIT` = *"Connected. Waiting for host to
  begin..."*, driven by `PEER_STATUS{peerCount>0}`, also transport-level and also unaffected.
- *"but then its stuck"* — steps 2 and 3. Permanently, with no error, no timeout, and no exit
  (A0-10).

**I am not claiming to have proven WHY verification fails in the owner's living room.** A0-2 says
the happy path works locally and A0-8 kills the strategy-identity theory. What is proven is the
**failure mode**: a single silent async predicate gates three independent recovery paths at once, has
no timeout, no user-visible diagnosis, and no fallback. That is the defect worth fixing whether or
not it is the only one — and it is exactly the shape that would produce the reported symptom.

## THE P4 MECHANISM (A0-13) — two defects, and a comment that contradicts its own code

`botBrain.ts:399-409`:

```ts
const savingForTower =
  world.matchPhase === 'BUILD' &&
  chooseTowerOrder(world, seat, cfg) !== null &&
  world.tick % SAVE_CYCLE_TICKS >= SAVE_HOLD_TICKS;
```
with `SAVE_CYCLE_TICKS = 3_600` and `SAVE_HOLD_TICKS = 1_800` (`botBrain.ts:82-83`).

**Defect 1 — the docblock and the code disagree by 2×.** Line 394 states: *"hold for
`SAVE_HOLD_TICKS` (90 s) of every `SAVE_CYCLE_TICKS` (120 s)"*. The constants are 1 800 (30 s) and
3 600 (60 s). The shipped hold is **30 s of every 60 s**, not 90 of 120. The session that wrote
"wrong by a factor of six in DURATION" then shipped a value wrong by a factor of three against its
own stated design.

**Defect 2 — the save window is anchored to ABSOLUTE tick, so it collides with the phase clock.**
Save windows are `tick mod 3600 ∈ [1800, 3600)` ⇒ absolute `[1800,3600) ∪ [5400,7200) ∪ [9000,10800) …`.
The real phase clock is BUILD `[0,5400)`, FIGHT `[5400,8100)`, BUILD `[8100,13500)`, FIGHT `[13500,16200)` …
Intersecting (the gate also requires `matchPhase === 'BUILD'`):

| Save window | Phase | Usable hold |
|---|---|---|
| `[1800,3600)` | BUILD | 30 s |
| `[5400,7200)` | **FIGHT** | **0 — wasted entirely** |
| `[9000,10800)` | BUILD | 30 s |
| `[12600,14400)` | BUILD then FIGHT | 15 s, then wasted |

So the longest contiguous hold a bot ever gets is **30 s**. The session's own measurement says income
is **~1 ordered shape / 11 s** and the cheapest bill wants **4 of one type ≈ 44 s**. 30 s buys ~2.7
shapes. **The pool can never reach a bill.** Zero towers is the arithmetically required outcome, and
`botTowers.test.ts` could not see it because it pins `matchPhase = 'BUILD'` for 3 unbroken sim-minutes
(10 800 ticks) — which contains whole 3 600-tick cycles and therefore a save window the real game
never gets.

This is the second time this feature was certified by an unrepresentative fixture. The fix is
therefore **written test-first against the real phase clock**, per the handoff's explicit instruction:
*"DO NOT loosen the assertion — write a test on the REAL phase clock, watch it fail, size the save to
BUILD-only income."*
