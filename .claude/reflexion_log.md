## S151 (2026-08-22) — the stat system, the goblin tower and its art; three priorities landed, and the defects that mattered had no failing test

_(6 entries. Highlights: a unit change is not tsc-forced the way a type change is; I committed a trap this repo documents in capitals; green tests prove code RUNS, not that a player can REACH it; and the owner's own arithmetic independently confirmed the model.)_

- #a-type-change-is-tsc-forced-a-unit-change-is-not - Renaming `Creature.hp` to `ehp` turned every unconverted read into a compile error, which is exactly what I wanted from a wide refactor. But the sites that PASS a number - `attackFifths(atk, pen)` versus a bare `1` - compile perfectly and silently deal one FIFTH of the intended damage, and no rename recruits the compiler for those. I had to enumerate them by hand: creatureAttack, the world raid, the defender fire site, the radial blast. The rule I want to carry is that when a quantity's MEANING changes rather than its shape, renaming it is the only move that makes the compiler an ally, and even then it only covers the read side.

- #my-own-automation-wrote-the-worst-bug-of-the-session - A patch script I wrote to add a field to 45 test literals also reached into `applySnapshotCore` - a PRODUCTION deserializer - and inserted a hardcoded `damageFifths: 0`. It compiled. It passed 2891 tests, because no fixture damages a bond. And it would have silently HEALED every damaged connector on every snapshot apply and every host migration: the same shape as the `despawnAtTick` 'detonation default' that this very file documents. I found it by reading the diff of everything the script touched rather than trusting the green suite. The blast radius of a regex is not the set of files you intended it to hit.

- #i-committed-a-trap-this-repo-documents-in-capitals - `blueprints.ts` says, at length and in capitals, do not value-import a recipe module from anything `world.ts` reaches, because every recipe calls `registerRecipe` at its tail. I read that warning while writing the goblin tower and then did precisely it, because my import looked like 'get the feed map' rather than like 'reach a recipe module'. The symptom pointed nowhere near the cause: a `?worker=1` bots match that never left TITLE with 198 polls throwing during boot. Reading a warning is not the same as recognising your own code as an instance of it, so the fix was structural - a side-effect-free leaf module - rather than remembering the rule harder.

- #i-overclaimed-causation-on-one-green-run-and-had-to-correct-it - I wrote 'CONFIRMS the cause' into a commit message after ONE passing re-run of the spec I had just fixed. In a repo where I had, that same session, measured a spec at 50% flaky and written a whole paragraph about quoting denominators. One green run after a change is a hypothesis; I re-ran it 3/3 before letting the claim stand, and amended the record in the next commit. The discipline is easy to apply to a result you distrust and easy to forget on the one you were hoping for.

- #green-tests-prove-code-runs-only-an-audit-proves-it-is-reachable - The goblin tower typechecked, had 34 passing tests, and shipped with three open pathways: it was IMMORTAL (no `recipeStillSatisfied` case, so its default arm kept it alive off one lone Circle), UNBUILDABLE (`ALL_BLUEPRINT_IDS` is a hand-written array, not exhaustiveness-checked like the `Record<GodlyId,…>` two lines above it), and its panel row had NO COPY. Nothing was red. I found all three by deliberately asking 'can a player actually reach this?', which is a different act from running the suite - and the array-versus-Record asymmetry is the kind of thing only that question surfaces.

- #the-owner-arithmetic-was-an-independent-oracle - I built the fifths model - `atk x (5+pen)` against `hp x (5+def)` - days before the owner sent their stat table. Their line for the chewer read '1 atk 2 pierce, 1hp, 0 def. so 1x1.4 offence, and 1 def', and the model produces exactly 1.4 and 1.0. That agreement is worth more than any test I could write, because it was derived from the opposite end by someone who had not seen the implementation. When a design can be checked against a source that did not come from you, that check outranks your own assertions.

## S150 (2026-08-22) — five priorities plus a sixth for owner rulings; a gate built in P1 paid for itself in P6; and the closing audit caught a regression I had shipped

_(11 entries. Highlights: enumerate a chain rather than reading it; instrument the failure before proposing a cause; a partial fix can look identical to no fix; and normalising a write path creates an obligation on every read path.)_

- #a-human-checks-the-last-link-a-machine-checks-every-link - I set out to repair two known gaps in the protocol changelog and found four, because I wrote a completeness check instead of reading the block. 8->9 had been missing since S93 and 20->21 since S144 - eight and three bumps, through multiple sessions that each read that comment and pronounced it complete, including two whose whole purpose was fixing this drift. The reason is structural: when a human validates a chain they check that the LAST entry matches the constant, because that is the cheap end-to-end check, and interior links are invisible to that method no matter how carefully you read. So the lesson is not 'read more carefully' - it is that any invariant of the form 'this sequence is complete' should be enumerated by code the first time you touch it, and the cost is fifteen lines.

- #my-first-gate-was-wrong-and-the-failure-was-the-most-useful-output - The chain test's first draft asserted both changelog carriers run from version 2, and it went red on the HelloMsg list for 2-6. My instinct was that I had found a sixth drift instance. I had not: that list was simply started later, at 6->7, and the FILE was right while my TEST was wrong. Had I 'fixed' the file to satisfy my gate I would have fabricated four changelog entries for bumps I know nothing about - the exact failure mode I had just finished refuting in two external reviewers. The design that came out of the failure is better than my first: measure each carrier's own floor, assert no gaps above it, pin the floors separately so deletions off the front still fail. When a new gate goes red, the first hypothesis to test is that the gate is wrong.

- #i-proved-the-gate-by-breaking-the-file-back - After repairing the drift I could have shipped a green test and called CF-S147-b closed. Green proves nothing about a gate: my assertions might have matched anything, or nothing. So I restored `git show HEAD:src/net/protocol.ts` over the working copy and ran the new block against the drifted file - it failed on exactly the three real classes and named the missing links [9, 21, 26, 27] out loud - then restored the repair and re-ran to 10/10. That round trip costs two commands and converts 'I wrote a test' into 'I watched this catch the specific bug it exists for'.

- #the-stubbed-test-was-green-and-the-real-browser-found-the-bug-in-one-frame - Nine unit tests passed against a Pixi stub and told me the overlay was correct. Then I drove the same three screens against real Pixi in the dev server, read back what was actually drawn, and immediately saw a board with two rows both reading 0:07.25 and the highlight on the wrong one. No stub could have shown me that, because the stub had no reason to produce a colliding board - I had written the fixtures, so my fixtures had my blind spot in them. The general lesson is not 'stubs are bad': it is that a stub tests the logic I thought of, and a live surface tests the DATA the system actually produces. When something renders, look at what it rendered.

- #i-could-not-screenshot-so-i-said-so-instead-of-implying-i-had - The browser pane cannot composite in this session and Pixi refuses synthetic pointer events, so two things I would normally verify - contrast and z-order - were genuinely unverifiable. The temptation was to let 'runtime-verified in a real browser' stand and leave the gap implied, since it is true and sounds complete. I wrote the limit into check_method explicitly instead, because this repo's recorded traps are exactly the visual ones and a future session reading 'runtime-verified' would reasonably assume the frame had been looked at. Verification claims should name their axis.

- #the-fourth-fixme-was-not-a-stale-test-and-i-had-written-it-up-as-one - My own PDR listed 'FOUR test.fixme, not three' as a finding and lumped all four together as stale surfaces. Reading the fourth one's BODY instead of its title changed the classification completely: it hardcodes `return null` and then asserts `not.toBeNull()`, so it has never been capable of passing, and it checks a '/50' readout from an era when the win score was 50 rather than 1500. Three stale tests and one placeholder are different problems with different fixes - the stale ones needed a new surface, the placeholder needs instrumentation that does not exist. The habit worth keeping: a `fixme` inventory built from grep gives you titles, and titles are the least reliable part of a test. Open the body before you size the work.

- #two-wrong-hypotheses-then-the-data-and-the-order-mattered - I spent this priority being wrong twice. The file's own comment blamed the AttractDrag; a probe showed the spark lands 0-2 px from the cursor, six times out of six. I then blamed the S149 phase boundary, proved placements really are refused after tick 5400, shipped a guard for it - and the guard never fired, because the real failures were at tick 2900. Only when I stopped proposing causes and instead made the FAILURE MESSAGE carry state did the answer appear in one line: rainbows=1. The lesson is about sequencing rather than humility: with an intermittent bug the cheapest first move is not a hypothesis, it is instrumenting the failure so the next occurrence indicts itself. I had the tooling to do that in five minutes and I did it fourth.

- #a-partial-fix-looked-exactly-like-no-fix-and-nearly-cost-me-the-real-one - Suppressing bombs took the failure rate from 2/6 to 3/8. Read naively that is 'no change, revert it' - and reverting would have been wrong, because bombs WERE genuinely stealing the mouse-down in the two failures I had measured. Two independent causes produced one symptom, and fixing one moved the rate by less than the noise in an n=8 sample. What saved it was the diagnostic printing bombs=0 on the NEXT failures: not a rate, but a direct statement that the first cause was gone and something else remained. When causes are independent and each is sufficient, pass rates cannot tell you whether a fix worked - only per-failure evidence can.

- #the-denominator-is-the-claim - Every number here is quoted with its trial count: 2/6 before, 3/8 after the partial, 0/8 after the full fix, and the lane 49/1/3 -> 53/0/0. That came from a prior session's note that 'flaky is a diagnosis that needs a denominator', and it earned its keep twice: it told me the bomb fix had NOT resolved things when the phrase 'fixed the bomb race' would have implied it had, and it is the only reason '0 fail' means anything now.

- #normalising-on-write-without-normalising-on-read-is-a-two-line-bug-in-one-commit - My P3 fix made recordRun store normaliseName(name) so a blank row could never reach the board. The overlay's highlight kept matching on the RAW initials, so a player who spelled three spaces had 'AAA' stored and '   ' searched for, and their own row silently stopped lighting up. Both halves were in the same commit and I wrote both. The shape to watch for is not 'normalisation is risky' - it is that adding a transform to a WRITE path creates an obligation on every READ path that matches on the written value, and nothing in the type system or the tests represents that obligation. The audit found it in one pass by asking what five keystrokes could produce.

- #a-one-constant-edit-crossed-the-wire-and-the-diff-gave-no-hint - VOLTKIN_HP 2 to 8 looked like a balance dial. It owed a protocol bump, because serializeCreature omits creature hp when the creature is UNDAMAGED - so an undamaged Voltkin carries no hp at all and the peer rebuilds it from its own compiled constant. An optimisation made in a different session for unrelated reasons (save bytes on the common case) had quietly turned that constant into shared state. The general rule, now written into the changelog with its three instances named: an additive-optional field whose ABSENCE means 'use your own default' makes that default a shared constant both peers compute from. Omitting a field to save bytes does not make its value private. The satisfying part is that P1's gate, built four priorities earlier in the same session, is what made the six-site bump mechanical instead of another drift instance.
