## S164 (2026-09-05) — V6-2.4 finished (castle regen, PROTOCOL 41), two shipped bugs found while verifying it, and the race-unit art

- S164 P1 #owner-number-checked-not-obeyed — THE OWNER GAVE A NUMBER THAT WOULD HAVE DELETED A WIN CONDITION, and the only reason it did not ship is that I did the arithmetic before writing code. "+1% hp reg per tick" is 1% x 1500 x 60 = 900 HP/s against a goblin's 6 — it out-heals 150 attackers, so the castle becomes unkillable at level 1 and the second victory condition stops existing. Putting the two columns (per-tick vs per-second) in front of the owner took one question and got a ruling. A brief is an intent, not a spec; the unit is the spec.

- S164 P1 #required-not-optional — MAKING THE NEW FIELD REQUIRED IS WHAT MADE tsc FIND THE TRAPS. castleRegenLevel could have been additive-optional like eliminatedAtTick, and eliminatedAtTick's own docblock records that an optional field omitted at the two carry-FSM rebuilds compiles clean and is silently reset on every spark pickup. Required turned that invisible class into four compile errors, one per construction site. Optional is the default reflex and it is the wrong one when a field must never be absent.

- S164 P1 #integers-are-the-design — THE RATE LANDING ON WHOLE HP IS NOT A COINCIDENCE, IT IS WHY THE DESIGN IS SAFE. 1500 x (1.0,1.2,1.4,1.6,1.8)% = 15,18,21,24,27 exactly, so regen is integer HP on a per-second tick cadence instead of a fractional per-tick accumulator this sim forbids. When a rate comes out clean, check whether that is load-bearing before treating it as luck — here it removed a whole class of determinism risk and a rounding rule that could have been got wrong.

- S164 P2 #docblock-as-bug-report — A COMMENT THAT CONTRADICTS ITS OWN CODE IS A BUG REPORT NOBODY FILED. creatureAttack said TWICE that the castle strike was "Ordered LAST, after bond / creature / shape" while the castle block returned above the bond branch. S157 F1 had fixed the SHAPE arm and stopped, leaving the connector family — exactly the family admitted to castle attacks — still underneath. The full suite was green before AND after the reorder, so nothing anywhere pinned the documented order; the regression test is the deliverable, not the reorder.

- S164 P3 #the-unvalidated-arm-is-the-important-one — damageEntity's castle arm returned ABOVE the integer/non-negative guard, so the ONE target that bypassed validation was the one whose HP ends the match: a negative amount added HP, unclamped. Worse, save.ts emits castleHp only when BELOW max, so any over-max value would have been emitted as nothing and read as 1500 by every peer — a silent divergence neither hash oracle can see. When a function has an early-returning special case, check what it is skipping on the way out.

- S164 P4 #separate-by-count-not-precedence — the boss tower ("nine of the race shape") collided with the NONET sweep ("exactly 9 of one type"), and the obvious fix was an ordering rule. The owner picked a better one: move NONET to 12. Neither trigger now needs to know the other exists, there is no precedence to get wrong, and both stay reachable. Prefer making two mechanisms disjoint over teaching one to defer to the other.

- S164 P5 #measure-the-art-do-not-eyeball-it — the owner reported white background in two units; a per-cell census found ~21,500 leaked pixels across ALL SIX, with nagas and demons worse than the two he spotted. The same census then proved the fix (94.2% removed) and caught the regression it caused (orc head-band light pixels 2267 -> 386, i.e. eyes going with the leaks). Art defects are as measurable as code defects, and offering to take screenshots instead of measuring would have been slower and less complete.

- S164 P5 #no-knee-means-fix-it-upstream — for the orc, leaked pockets and eye whites are the SAME SIZE (43..320px vs eyes to 38px, overlapping), and the measured curve across five thresholds moved both together monotonically with no knee. That is the signal that the lever is wrong, not mis-tuned: the real fix is at generation (stop producing eye-sized white pockets, stop baking a shadow the renderer already draws in the owner tint). Took the balance point, filed the source fix, said so plainly rather than pretending the knob solved it.

- S164 P5 #the-tool-already-knew — every art defect this session was one the pipeline had already documented for a previous character: the sampleWindow docblock describes veo drifting after ~1s (the naga's size incoherence), and the matte docblock describes sub-threshold enclosed pockets shipping as blobs (the wing gaps, "one size band down" for the bat rider). Reading the script's own comments before retuning it would have predicted all three. Check whether the tool has already met this bug.

- S164 SESSION #reversal-can-be-coherent — the owner asked for varied tier-3 unit stats, which directly reverses R117 (his own ruling, which killed that idea once). Rather than either obeying silently or objecting, the right move was to find WHY R117 existed: it rests on the castle and the tower emitting the same creature, and the owner's new split makes them different creatures, so the exploit R117 guarded against is gone by construction. A reversal that dissolves its predecessor's premise is not a contradiction — but it has to be written down as one, at the ruling.
