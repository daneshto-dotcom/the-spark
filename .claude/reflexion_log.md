## S159 (2026-09-02) — seven priorities: two R77 mechanics, two lying gates, and a sweep that found the owner's own bug still live in a fourth place

- **S159 P1 — THE CHEAPEST VERSION OF A CARRIED-FORWARD PLAN CAN BE A DIFFERENT PLAN.** Two handoffs carried bag aggro as *"needs a new committed-target field on `Creature` (wire + hash + protocol bump)"*, reasoned by analogy with the depleted tower's taunt — which needs a field because it writes `targetPrimitiveId` and a tower HAS an anchor primitive to point at. The codebase had already written down both tests for when a committed target must be STORED (several sites must agree within one tick) and when it needs HYSTERESIS (the target moves); a bag fails both, so the feature is a derived scan, `Creature` is byte-identical and PROTOCOL_VERSION never moved. **Before paying a carried-forward cost, re-derive it — a handoff's SHAPE is a claim too, not just its numbers.**

- **S159 P1 — A NEGATIVE CONTROL IS WORTH MORE THAN THE ASSERTION IT PROTECTS.** With the four-line steering insert removed, the bag still DISAPPEARED — it expired on its own 4-second timer — so "the bag is gone" passes on a completely unwired build. The shipped rule is endpoint `placerColor` against the owner's LIVE colour, because a captured shape keeps its original allegiance for targeting and a rainbow shuffle remaps colours without touching `placedBy`. **When a rule already exists as an exported function, call it** — the cost of re-deriving is not the typing, it is that the two copies drift and only one is tested.

- **S159 P2 — DIFFERENTIAL GUARDS DO NOT NOTICE A DELIBERATE BEHAVIOUR CHANGE, AND THAT CUTS BOTH WAYS.** Three files are documented as pinning Voltkin behaviour byte-identically, and all three stayed green through a change that gives it five extra targets per strike — because they compare two SIMS, not a golden value. Nobody fixed it because the warning was cheaper to write than the diagnosis. **A stale gate output is a bug report about the gate, not a note for the reader** — and the fix prints the KEY it read, so the next drift shows up on the card instead of needing an investigation.

- **S159 P4 — RENAMING THE FILE WOULD HAVE SILENCED NOTHING.** Three archived plans made the boot warn every session, and the obvious fix — rename `*_IN-PROGRESS.md` — is the wrong one: `pre-flight.sh` greps `plans-archive/*.md` for a STATUS LINE **inside** the file. - **S159 P5 — I BROKE THE "NEVER READ AN EXIT CODE THROUGH A PIPE" RULE IN THE COMMAND THAT WAS CHECKING COMPLIANCE.** `verify-session-claims.py … | tail -2 && git commit` reads TAIL's status, so a `hard_fail=2` verdict scrolled past and the commit went through. ## S158 (2026-09-01/02) — sixteen priorities: the owner's carry-forwards, then the owner reviewed the batch and sent me back to the record twice

> ⚠ 38 entries were staged this session; the twelve with distinct, transferable lessons are kept here. The full set lives in `.claude/session-state.json` (`reflexion_entries_to_archive`) and the handoff doc, both archived — nothing is lost, but a 38-entry block would have pruned most of the log's history to make room for restatements of the same four ideas.

- **S158 P1 — THE FIX FOR A FIX WAS A DEAD END, AND NOBODY WOULD HAVE FOUND OUT.** S157 correctly diagnosed the TURN outage and then wrote a runbook that could not work: `.env` is gitignored and CI builds from a clean checkout, so the owner's five-minute action would have ended in a green deploy and a still-broken game. The lesson is narrow and repeatable: **when the last mile of a fix is an OWNER ACTION, trace that action end-to-end through the machinery that actually ships, not the machinery on your disk.** I also probed the mechanism before building on it (built with a fake value, grepped it out of the bundle) — one minute, and it also proved the credential is public in the shipped JS, a fact the runbook now tells the owner instead of letting them discover it.

- **S158 P2 — A HANDOFF NUMBER IS A CLAIM, NOT A MEASUREMENT.** The handoff said 3220/3220; the boot measured 3219/3220. Same code, different machine load. Re-running the suite at boot cost twelve seconds and found a deploy gate that had become a coin-flip. And the cause is a category worth naming: **turning a limit off by RAISING its constant is a performance change in disguise** — S157 set three caps to 10,000, and four tests that loop to `CAP + k` with an O(n) scan inside became O(n²) overnight. Nothing in that diff looks like it touches test cost.

- **S158 P2 — FIXING THE COST EXPOSED THAT THE TESTS PROVED NOTHING.** With all three caps equal, the global one bites at the same count, so the per-victim and per-spawner assertions were satisfied by the wrong rule and would have passed with their branch deleted. A test that is expensive is worth reading closely; **the expense is what made me read it.**

- **S158 P3 — A BRANCH THAT WAS CORRECT WHEN WRITTEN BECAME WRONG WITHOUT ANYTHING FAILING.** `if (selfExplode) … else if (targetsStructures)` was unambiguous while no creature was ever both. The goblin roster made one both, and the else-if silently handed it the drone's whole identity. When a config grows a case an old branch never considered, nothing goes red — the flags just quietly mean something new. Fix by NARROWING the old branch, not reordering: `&& !targetsStructures` kept every shipped creature byte-identical, where a swap would have moved code three replay guards pin.

- **S158 P4 — A CARRY-FORWARD IS A CLAIM WITH A TIMESTAMP.** CF-S157-f said an aborted cinematic "burns that godly for all players". True when written; false by the end of the same session, because a later priority removed the gate. **Re-measure a carry-forward before fixing what it says** — and fix it anyway when a later priority is about to make it true again.

- **S158 P5 — THE DEFERRAL'S HAZARD WAS RIGHT AND ITS PRESCRIPTION WAS TOO BIG.** S157 said the cutscene fix needed the cinematic's TIMING moved into the sim. The hazard (the overlay's `onComplete` is the sole completion driver) is exactly right and is what the fix is built around — but timing does not have to MOVE to be separated from visuals, only to keep RUNNING while the visuals do not. **Read a deferral's DIAGNOSIS carefully and re-derive its PRESCRIPTION.** Also: for "play the cutscene once", the tempting assertion is "the second one is silent" — which passes against the latch that would freeze every later Voltkin. The assertion that earns its keep is "the silent one STILL completes, on the same schedule to the millisecond".

- **S158 P6 — THE ANTI-VACUITY GUARD FOUND A DEAD FEATURE, NOT A DESYNC, AND THAT WAS MORE USEFUL.** I asserted a new family SEEDED in the worker differential; the harness said it was empty across 300 frames. The tempting move is to demote the row to "acknowledged" with a plausible reason. **Probing instead found that S157's blind lob had never fired once** — the fix shipped, its comment shipped ("A BLIND LOB STILL LANDS"), and the code path between them did not. An empty seeding row is a question, not a chore. Corollary: **a comment describing behaviour is not evidence of it** — confident prose is exactly where to point a test.

- **S158 P6 — SHIP THE WHOLE VERTICAL SLICE OR NONE OF IT.** A new entity family touched 14 sites: id brand, entity, host tick, serialize, protocol bump, FIELD_COVERAGE, hash projection, structuralSignature, differential seeding, three teardowns, renderer, z-order manifest. - **S158 P8 — MY OWN FIX BROKE A GATE, AND ONLY THAT GATE NOTICED.** P1's CI `env:` block made an unset secret arrive as `''` rather than nothing, so CI and local builds emitted different bytes for identical source and `verify-deploy`'s content-hash carrier went red on a good deploy. Every test was green. **Adding env to a build changes the BUILD, not just the behaviour** — and run the deploy verifier at the close even when nothing about deployment was the priority. **A gate that cries wolf is worse than no gate**, which is the same argument P2 made about a flaky test, arriving from the opposite direction the same day.
